# Working on Lichterhain

Read README.md, DECISIONS.md, TASKS.md, TESTING.md, docs/CREATIVE_DESIGN_BIBLE_V1.md, and the current foundation report before extending this project.

- Preserve Tim's choices: mysterious, colorful fantasy; slightly angled top-down pixel art; mage first; Godot 4 and GDScript; offline singleplayer.
- Follow ROADMAP.md. Tim accepted M07 and confirmed the Sandbox mouse-fix Windows retest on 2026-10-05. M08 Weapon Foundation is now authorized; M09 is not. Read docs/M08_ARCHITECTURE_REVIEW.md, docs/FUTURE_SYSTEMS_BLUEPRINT_V1.md and the approved M08 Gameplay / Systems Design Specification V1.0 before implementing weapons. The Implementation Prompt is available, but the separately referenced gameplay specification has not yet been supplied in the available project files. Finish that reference check before choosing gameplay rules. Preserve M06 numerical resolution and M07 lifecycle/contact/defense/reaction ownership, keep sandbox loadouts transient, and stop after M08 tests, exports and completion report. Never touch production saves.
- Read docs/M06_STATS_HIT_RESOLUTION_V1_1.md before changing hit behavior. HitResolver is pure shared damage/impact mathematics; existing combat supplies contact and DefenseOutcome, actors/Vitals own health and responses. Preserve the specified formulas, minimum damage, separate impact and explicit immunity. Capture a HitInstance at attack/pulse creation and reuse it for deliveries; it checks its weak regional CombatSystem scope and claims each target before signals. New pulses need explicit new instances. No timing/detection, global hit registry, secondary-effect execution or progression inside the resolver. See TECHNICAL_DESIGN.md for the actual API and compatibility-entry limits.
- InteractionCore is a session-local synchronous contract, not a gameplay owner. Capture lifecycle identity/generation and weak actor/target references when creating a request; recheck the chosen offer and consumer conditions immediately before resolution. Discovery/validation must be pure and synchronous. RunState/Vitals retain rules and mutations; confirmed results precede consumer presentation/save checkpoints. No global verb list, condition engine or event bus. See TECHNICAL_DESIGN.md for the exact supported contract and limits.
- JSON definitions are loaded once and recursively read-only through Content. Maintain ContentValidator/VaultContentValidator alongside supported fields. Gameplay and UI must use these definitions; no independent copies of balance values. Tests may explicitly substitute a private copy; runtime consumers may not mutate content. Preserve schema 3 and absolute saved resources when maxima change; serialization limits are not gameplay maxima.
- Lichterhain is permanently a 2D-isometric fantasy RPG. Do not add 3D preparation, streaming, an autoload RegionManager or a global event bus. RegionLifecycle belongs to the game session; RegionInstance owns the single replaceable 2D tree.
- Persistent progress remains in RunState. A region generation is transient and monotonic across travel/load/new-run within the lifecycle. Delayed actions reaching outside the old tree must capture their originating generation and validate it at delivery; never look up the new generation only when delivering an old request.
- Runtime progression requests go through RunState's domain actions. DungeonProgress, SourceQuest and RelicInventory retain their local rules; RunState coordinates their rewards and emits changed only after the complete persistent result. Scene code owns presentation and explicit save checkpoints. Tests/restoration may construct fields directly; do not add direct progress writes in scene/combat/UI code.
- The creative Bible owns the intended experience; TECHNICAL_DESIGN.md owns the implemented architecture. Flag conflicts instead of silently weakening the vision. Explicitly open design details remain open; new details are PROPOSAL until Tim confirms them. Before a future feature, check priority, dependencies, foundation readiness, architecture changes and tests.
- The mage is the first prototype playstyle, not a permanent class restriction. Preserve the Bible's freedom, meaningful consequences and optional depth.
- Preserve the original 0.4 release at GitHub reference/v0.4-original. M00 only adds documentation, baseline evidence and frozen reference saves. Do not regenerate or overwrite any frozen fixture to make a later test pass.
- Keep balance definitions in data/content.json and actor/state/UI responsibilities separated.
- Pin development and export to Godot 4.5.1 for this baseline. Investigate and document any deliberate upgrade.
- Run the relevant Godot tests after gameplay changes. Tests write only their dedicated test save paths. Render affected UI before shipping layout changes.
- Preserve stable world IDs and save compatibility; a generator/schema change needs a deliberate migration or version policy.
- Update the short project documents when behavior or priorities change. Distinguish implementation, automated validation, and human playtesting.
- Work only in the RPG repository selected by the user. MyFire belongs to another project.
- Pixel graphics are original code-defined assets. The DejaVu heading font is bundled with its license. Track provenance for new external assets.
- Preserve the frozen 0.1 fixture: never regenerate it with current code just to pass the compatibility test.
- Preserve the completed 0.2 fixture as well. Schema 1 migrates explicitly to schema 2; never overwrite the original .pre-v03 backup during later saves.
- Preserve the completed 0.3 fixture. Schema 3 explicitly migrates schemas 1/2 and keeps a permanent .pre-v04 original, including backup recovery. Do not overwrite prior migration backups.
- Quest rewards and source outcomes are one-time decisions. Scene reloads reset the live guardian, never the outcome, investigation checkpoint or equipped relic. Keep source progression separate from scene nodes.
